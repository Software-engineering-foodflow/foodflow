## 2. 系統背景與問題定義

單一門市餐廳以紙本或試算表記錄食材，容易遺漏效期、先後使用順序及存放位置，也不易追查浪費原因。FoodFlow 以進貨批次保存來源、到期日、位置與剩餘量，透過 FEFO 建議、效期與低庫存提醒協助員工安排工作。領用、報廢及盤點均留下異動，使期初與期末可以核對。

目前沒有實際餐廳試用數據，因此不承諾特定浪費降低比例。效期狀態依輸入資料與規則判定，不代替現場食材狀況檢查。

## 3. 利害關係人與需求

| 利害關係人 | 需求 | 對應成果 |
| --- | --- | --- |
| 餐廳負責人／店長 | 掌握存量、損耗及差異；管理帳號與主檔 | 管理者權限、庫存及報廢報表 |
| 收貨／採購人員 | 記錄來源、批次、數量、日期與位置 | 進貨確認、批次追溯 |
| 廚房／備料人員 | 找到食材、優先使用適當批次、登記耗用 | FEFO 領用、預警、報廢 |
| 授課教師與組員 | 需求、設計、程式與測試可相互核對 | 文件、原始碼、測試證據及展示 |

系統權限採管理者與一般員工兩種角色。功能是否允許由伺服器檢查，不能只隱藏前端按鈕。

## 7. 依賴與風險管理

| 風險／依賴 | 影響 | 對策與追蹤 |
| --- | --- | --- |
| 本機未配置 PostgreSQL 與測試 URL | 真回滾／列鎖／查詢尚無執行證據 | 在有 PostgreSQL 的環境重跑整合案例；不以 fake 冒充通過 |
| FR-16 原始需求比舊 AD-8 嚴格 | 只比數量會漏掉改回同量 | 依原始要求採數量＋最新異動編號，記錄差異；不改共用帳本或 schema |
| 隊友預警、進貨、領用、完整庫存頁尚待整合 | 無法完整走通 SRS 第 9 節 | 交付共用全數報廢 hook/dialog；安排 11/11 整合驗收 |
| 同時扣量與網路重試 | 負庫存或重複報廢 | StockLedger 列鎖、同交易寫入、Idempotency-Key 與 PostgreSQL 競態測試 |
| 報表日期、沖銷與單位混算 | 報表失衡 | 台北半開日期區間、原類型歸類、按鍵與單位分組、未知成本事件明列 |
| 金額權限洩漏 | 員工取得管理者資訊 | 伺服器分角色 schema，分布 API 管理者守衛 |
| AI 產出錯誤／介面整合衝突 | 實作與需求脫節 | 規格對照、測試、lint、互審，保留失敗與待驗記錄 |
| 平板觸控及 bundle 大小未充分驗收 | 操作不便或首次載入較慢 | 保留兩種尺寸人工驗收；現有 chunk 警告不隱藏，效能於實機確認 |
| 進度延誤 | 整合與報告準備時間壓縮 | 優先補真 DB 驗證與共用接口，再處理非必要延伸 |
