## 2. 系統背景、定位與問題定義

### 2.1 問題背景
單一門市餐廳日常營運若仰賴紙本或試算表記錄食材，進貨時常遺漏保存期限，廚房備料時憑印象拿取，容易發生先進後出導致過期報廢，或用完才發現缺料；此外，存放位置分散與人工記錄缺乏完整異動歷程，使店長難以追查實際耗用與浪費原因。

### 2.2 系統定位與解決方案
「食序 FoodFlow」定位為**單一門市、非連鎖獨立餐廳（不限規模）**之 Web 食材庫存與效期預警系統，支援電腦與平板瀏覽器操作。系統以**「庫存批次（InventoryBatch）」**為追蹤核心，分別記錄每批進貨的來源供應商、到期日、儲存位置、進貨單價與剩餘量，並嚴格區分「實體庫存量」與「可用庫存量」。

透過「先到期先使用（FEFO）」領用建議、站內效期與低庫存預警、報廢成本統計及盤點差異調整，系統將進貨、領用、報廢與盤點串接為可追溯的閉環，使期初與期末庫存可透過帳本異動完整核對。

### 2.3 邊界與成效說明
- **首版系統邊界：** 專注於單店 Web 作業與站內即時預警，不包含多門市跨店調撥、菜品食譜與 POS 銷售自動扣料、自動採購下單、會計付款、條碼／OCR 硬體辨識，以及 Email／LINE 外部推播通知（列為期末評估延伸項目）。
- **成效與責任界定：** 目前無實際餐廳導入試用數據，因此不預設特定損耗降低百分比；效期狀態依人員輸入之日期與規則判定，不取代餐廳人員對食材實際品質與食用安全的現場檢查。

## 3. 利害關係人與需求

| 利害關係人 | 核心需求 | 對應系統成果 |
| --- | --- | --- |
| 餐廳負責人／店長 | 掌握全店存量、效期風險與損耗金額；維護員工帳號、主檔與預警規則；執行盤點與異常沖銷 | 管理者權限控制、主檔維護、盤點調整、進貨沖銷、庫存與報廢分布報表 |
| 收貨／採購人員 | 登錄供應商與進貨明細，保存批次來源、數量、單價、到期日與存放位置；掌握缺料品項 | 進貨草稿與確認入庫、批次來源追溯、低庫存預警 |
| 廚房／備料人員 | 快速查詢食材位置與效期，依 FEFO 優先順序領用，即時登記耗用與報廢 | FEFO 領用建議、非 FEFO 原因登記、效期預警、報廢與一鍵全數報廢 |
| 授課教師與專題組員 | 需求、分析、設計、程式碼與測試證據相互對齊且可重現驗證 | A～G 完整專題文件、前後端原始碼、自動化測試報告與期中／期末展示 |

系統權限採**管理者（ADMIN）**與**一般員工（STAFF）**兩種角色，所有功能存取與敏感資料（如報廢損失金額）均於伺服器端進行驗證，不依賴前端介面隱藏按鈕。

### 4.2 非功能性品質需求（NFR-01～NFR-08）

| 編號 | 品質維度 | 驗收與設計重點 |
| --- | --- | --- |
| NFR-01 | 裝置與易用性 | 全繁體中文介面，支援 1024×768 平板橫向與 1366×768 電腦螢幕無橫向捲動；狀態以文字與顏色並用，關鍵操作可觸控（目標 ≥ 44px） |
| NFR-02 | 資料一致性 | 併發領用不超扣、網路重試不重複入庫或扣量（單據狀態機、`Idempotency-Key`、盤點帳面量與最新異動編號雙重檢核），交易失敗全數回滾 |
| NFR-03 | 可追溯性 | 所有數量變動記錄操作者、時間（Asia/Taipei）、來源單據與前後數量；位置變更獨立記錄，可由帳本重算目前庫存 |
| NFR-04 | 安全與權限 | 密碼採 Argon2 雜湊儲存；JWT 透過 HttpOnly Cookie 傳遞並驗證 `token_version`；伺服器端強制角色授權；對外部署啟用 HTTPS |
| NFR-05 | 錯誤回饋 | 明確標示錯誤欄位路徑並保留已填表單內容；後端確認成功後才顯示完成提示 |
| NFR-06 | 資料保存 | 容器重啟後持久化保留資料；提供 `backup.sh` 與 `restore.sh` 備份還原程序及帳本一致性核對指令（`verify-stock`） |
| NFR-07 | 效能規模 | 以 500 項食材、5,000 個批次、20,000 筆異動及 10 人同時操作為測試基準，95% 查詢於 3 秒內完成（排定於期末執行負載測試） |
| NFR-08 | 可維護性 | 採用課程設計層次 4（API → Service → Repository 分層），庫存寫入集中於 `StockLedger`，批次回選、預警規則與通知分別以 Strategy、Factory、Adapter 隔離 |

### 4.3 技術選型摘要
- **前端：** React 19、TypeScript、Vite、Mantine 9 UI 元件庫、TanStack Query（快取與狀態同步）、React Router。
- **後端：** Python 3.13、FastAPI、SQLAlchemy 2、Alembic（資料庫遷移）、Pydantic v2（三位小數精度驗證）、`import-linter`（架構分層靜態檢查）。
- **資料庫與環境：** PostgreSQL 17（12 張正規化資料表，採 `NUMERIC(12,3)` 儲存數量與列鎖控制）、Docker Compose。

## 7. 依賴關係與風險管理

| 風險／依賴項目 | 潛在影響 | 緩解對策與目前追蹤狀態 |
| --- | --- | --- |
| **開發機環境差異（PostgreSQL／Docker 未啟動）** | 部分成員本機未配置 `TEST_DATABASE_URL`，導致真資料庫交易回滾、列鎖與 SQL 查詢整合測試無法直接執行 | 單元測試與前端測試（如報廢／盤點／報表模組 189 項後端與 125 項前端測試）均已通過；整合測試嚴禁以 fake 冒充通過，統一於已啟動 Docker PostgreSQL 的環境重跑 `pytest tests/integration` 與 `alembic check` 補齊證據 |
| **多模組併發扣庫存與網路重試** | 多人同時領用或斷網重送可能造成負庫存或重複入庫／扣量 | 統一由 `StockLedger` 依 `batch.id` 遞增進行資料庫列鎖（`FOR UPDATE`），並搭配進貨狀態機、`Idempotency-Key`（領用與報廢）及帳面量＋異動編號雙重檢核（盤點） |
| **跨模組整合與快取不同步** | 進貨、領用、報廢或盤點後，首頁預警與庫存總覽數量未即時更新 | 前端統一透過 `shared/api/queryKeys.ts` 管理快取鍵，所有庫存異動 Mutation 成功後呼叫 `invalidateStockQueries()` 同步刷新相關頁面 |
| **文件與程式碼演進脫節** | B、C、D 文件與實際類別名稱、API 路徑或欄位定義不一致 | 嚴格遵守 `CONTRIBUTING.md` 命名規範，由 `openapi-typescript` 自動生成前端 `schema.d.ts`，並於 11/13 進行全組文件交叉核對 |
| **AI 輔助開發產生邏輯偏差或幻覺** | AI 產出程式碼可能違反分層架構、漏掉邊界條件或洩漏敏感欄位 | 透過 `ruff`（禁用系統時間）、`import-linter`（4 條架構契約）與 `eslint`（禁止跨 feature 呼叫與寫死色碼）自動把關，所有 AI 錯誤與人工修正均記錄於 `docs/ai-log.md` |
| **前端 Bundle 體積與平板觸控體驗** | Vite 建置出現大於 500 kB chunk 提示，且需確保 1024×768 平板橫向操作流暢 | 保留警告追蹤不隱藏，於 11/16～11/17 彩排前完成 1024×768 與 1366×768 兩種解析度的完整人工操作驗收 |
