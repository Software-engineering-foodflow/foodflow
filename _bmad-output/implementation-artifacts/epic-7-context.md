# Epic 7 Context: 效期與低庫存預警首頁

<!-- Compiled from planning artifacts. Edit freely. Regenerate with compile-epic-context if planning docs change. -->

## Goal

讓員工登入後即掌握需要處理的過期、今日到期、即期批次與低庫存食材，安排領用、報廢或補貨；管理者能設定全店預警天數。預警依目前庫存與台北日期重新計算，呈現可核對的數量、位置與更新時間。

## Stories

- Story 7.1: 效期預警清單
- Story 7.2: 低庫存預警
- Story 7.3: 預警篩選與前往處理
- Story 7.4: 從過期預警一鍵報廢
- Story 7.5: 設定預警天數

## Requirements & Constraints

- 效期狀態互斥：距到期日小於0為過期、等於0為今日到期、1至預警天數為即期；其餘不提醒。預設提前3天；設為0時不產生即期提醒。今日可領用，過期不能領用。
- 只有剩餘量大於0的批次產生效期預警。食材停用仍須處理既有批次；過期不自動扣庫存，歷史資料保留。
- 低庫存條件為全店可用量小於或等於安全量，且安全量大於0；可用量排除過期量。從未進貨的啟用食材也可能低庫存，停用食材不提醒低庫存。缺口不能為負，等於安全量時仍提醒。
- 狀態與位置可篩選。位置不能改變全店低庫存判定；篩選後僅顯示在該位置有剩餘批次的低庫存食材，位置量與全店量須區分。
- 載入、重新整理及庫存異動成功後重查；顯示伺服器產生時間，不把舊資料當作最新資料。
- 一般員工可查詢與處理預警，只有管理者可修改預警天數。負數、小數、非數字必須被拒絕，錯誤保留輸入且指出欄位。
- 首版只有站內提醒，沒有排程、Email、簡訊或 LINE。大量資料效能測試安排於期末。

## Technical Decisions

- 採 Controller、Service、Repository 分層；Service 使用注入介面，不直接依賴 HTTP 或 SQL 實作。交易由 UoW 管理。
- 四種規則各自實作 AlertRule，由 AlertRuleFactory 依設定組合；規則只讀不可變快照。增加規則不改既有規則。
- 預警即時計算，不存表。AlertService.evaluate 僅計算；list_alerts 再交給注入的 InAppNotifier，以 API 回應投遞。外部通知需另由獨立進入點觸發。
- 後端決定過期、今日、即期、低庫存的優先序；同級按到期日、食材識別碼排序。回應提供 generated_at 與 actions，過期動作沒有領用，一鍵報廢帶明確剩餘量快照與過期原因。
- 日期來自可注入 Clock，以 Asia/Taipei 計算；數量使用 Decimal、最多三位小數，JSON 使用字串。
- 設定維持單列，讀取固定選最小識別碼；更新記錄操作者與時間。
- 前端請求經 API 層與 TanStack Query hooks；預警與庫存的 staleTime 為0。庫存及設定寫入成功後共同失效相關快取，狀態與數量不得由前端重算。

## UX & Interaction Patterns

- 森林綠主題與現有共用元件一致：頁首、摘要卡、主卡片內工具列與資料表。狀態顯示文字及顏色；過期、今日到期較強，即期較弱。
- 批次清單顯示食材、批號、位置、數量、單位、到期日與剩餘天數；低庫存顯示食材、可用量、安全量與缺口。
- 操作連到領用、指定批次報廢或指定食材建立進貨單。全數報廢須確認快照，失敗不顯示完成，併發衝突需提示最新量並重新核對。
- 管理者設定入口對一般員工隱藏，伺服器仍驗權限。載入、錯誤、重試及無預警狀態均須可辨識。
- 1024×768與1366×768無水平捲動；互動目標至少44px、輸入有標籤，操作不依賴 hover。

## Cross-Story Dependencies

- 基本資料提供安全庫存量；進貨、領用、報廢、盤點改變庫存，均需讓預警刷新。
- 一鍵報廢使用報廢模組提供的 hook 與確認元件，不另建扣庫存流程；保留既有交易、重送與衝突保護。
- 庫存總覽與預警共用庫存查詢及低庫存規則，避免位置篩選或過期量造成判定分歧。
